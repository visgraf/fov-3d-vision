# Step A1 — scene gathering

Run order, acceptance checks, and what has been verified. Commands are run from the
repository root. See `../README.md` for the project and `../DECISIONS.md` for the standing
decisions this rests on.

Three tiers of scenes, each checked by a 360° preview from a fixed eye position.
With the head fixed, that one panorama is everything a rotating eye can ever see from there,
so it shows at once whether a scene is usable.

| Tier | Scene | Why |
|---|---|---|
| 1 | Poly Haven HDRI | Environment at infinity: exactly a function on the sphere, and the HDRI file is its own ground truth |
| 2 | Calibration room (generated) | Known targets at known eccentricities and distances; foveation falloff is visible at a glance |
| 3 | Realistic interior (Blender demo file, e.g. Classroom) | Photorealism; must be complete in every direction from the eye |

## Setup (Linux box)

```bash
# Blender 5.2.1 LTS on PATH as `blender`
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt   # for inspect_preview.py
```
`fetch_hdris.py` needs only the standard library, and the Blender-side scripts run inside
Blender's own Python, so the venv exists solely for `inspect_preview.py`.

The repo carries the tools, the manifest, and the CPU reference sheet — about 2 MB. Scenes and
previews are deliberately absent: they are either generated by the commands below or downloaded
by them, and `workshop_8k.exr` alone is 324 MB. Run the tiers in order and they rebuild.

## Run order

**Tier 2 first** (no downloads; exercises the whole chain):
```bash
blender -b -P tools/make_calib_room.py -- --out scenes/calib_room/calib_room.blend
blender -b scenes/calib_room/calib_room.blend -P tools/preview360.py -- --out previews/calib_room
.venv/bin/python tools/inspect_preview.py previews/calib_room
```
Expect `hole_fraction` 0, `backface_fraction` 0, nadir and zenith depth 1.60 m (eye at 1.6 m, ceiling 3.2 m).
`calib_room.targets.json` lists every target with its direction, eccentricity, distance and angular size.

Two images in `docs/reference/` record what this tier looked like when it was built, on CPU:

* **`docs/reference/calib_room_sheet.png`** — the contact sheet. This is the baseline to compare your
  own `previews/calib_room/sheet.png` against: same room, same ring layout, and a problems panel
  that is clean greyscale throughout. It is how you tell a rendering-backend problem from a scene
  problem, since a change of device should leave it structurally unchanged.
* **`docs/reference/calib_room_center_34deg.png`** — a 34° rectilinear view from `EYE` along the
  primary gaze, as against the 360° equirect the tools produce. It shows the Siemens-star cards on
  the 0°, 2.5°, 6° and 12° rings with their eccentricity labels (the 24° and 40° rings fall outside
  this field, clipped at the corners), which makes the card-size law
  `alpha(e) = alpha0 * (1 + e / E2t)` visible directly: the cards grow with eccentricity so that a
  foveation warp with `E2 = E2t` should render every ring about equally sharp.

**Tier 1:**
```bash
python3 tools/fetch_hdris.py list --environment indoor --min-width 16384 --top 30
python3 tools/fetch_hdris.py get <slug> --res 8k --out scenes/hdri
blender -b -P tools/make_hdri_scene.py -- --hdri scenes/hdri/<slug>/<slug>_8k.exr --out scenes/hdri/<slug>/scene.blend
blender -b scenes/hdri/<slug>/scene.blend -P tools/preview360.py -- --out previews/hdri_<slug> --width 2048 --spp 16
.venv/bin/python tools/inspect_preview.py previews/hdri_<slug> --hdri scenes/hdri/<slug>/<slug>_8k.exr
```
Expect `hdri_check.column_shift_px` = 0 and `rel_err_median` around 1% or less.
Keep `--width` a divisor of the HDRI width (8192 → 2048) so the comparison uses box averaging.
Pick HDRIs with fine detail at many directions; 8k (22.8 px/°) covers a reference at s₀ = 0.05°.

`column_shift_px` is the check that matters: it is the one that fails if the mapping is wrong.
`rel_err_median` also counts the reconstruction filter, so on a high-frequency source the default
Blackman-Harris filter lands around 1.5% no matter how many samples you throw at it. To compare
like with like, render the identity check with the box filter that `inspect_preview.py` itself
applies to the source:

```bash
blender -b scenes/hdri/<slug>/scene.blend \
  -P tools/preview360.py -- --out previews/hdri_<slug>_boxfilter --width 2048 --spp 256 \
  --no-backface --filter BOX
.venv/bin/python tools/inspect_preview.py previews/hdri_<slug>_boxfilter --hdri scenes/hdri/<slug>/<slug>_8k.exr
```
That is the only way to read the number as a statement about the mapping rather than about
filtering: on `workshop` 8k it takes `rel_err_median` from 0.0152 to 0.0032 and p99 from 0.23 to
0.047. It is a diagnostic, not the scene you keep — hence the separate `--out`, which also keeps
`--no-backface` from leaving a stale `backface.exr` next to a fresh `pano.exr`.

**Tier 3:**
1. Download Classroom (`https://download.blender.org/demo/test/classroom.zip`, 70 MB) into
   `scenes/classroom/`. It is CC0 by Christophe Seux; record that in the manifest. The zip
   unpacks into a nested `classroom/` directory — flatten it, keeping `classroom.blend`,
   `textures/` and `assets/` together, or the relative texture paths break.
2. First look, from the file's own shot camera (the script falls back to it when there is no `EYE`):
   ```bash
   blender -b scenes/classroom/classroom.blend -P tools/preview360.py -- --out previews/classroom_shotcam --spp 64 --denoise
   .venv/bin/python tools/inspect_preview.py previews/classroom_shotcam
   ```
3. Place `EYE` at a seated eye position (about 1.2 m), aimed along the primary gaze and level.
   Either in the GUI (*Add → Camera*, name it `EYE`, check with Numpad 0, save), or headlessly
   with `tools/place_eye.py`, which records the vantage point as a number instead of a mouse
   gesture. `--dry-run` prints the scene bounds and every existing camera's pose, which is how
   you pick the arguments:
   ```bash
   blender -b scenes/classroom/classroom.blend -P tools/place_eye.py -- --dry-run
   blender -b scenes/classroom/classroom.blend -P tools/place_eye.py -- \
           --location -0.6 -1.0 1.2 --yaw 0 --out scenes/classroom/classroom_eye.blend
   ```
   Save beside the original so its relative texture paths still resolve, and leave the demo file
   itself untouched. Then re-run `preview360.py` and `inspect_preview.py` on the new file into
   `previews/classroom`.
4. If it fails the checks, try another interior demo file, then Infinigen Indoors.

Do not expect the file's own shot camera to work as an eye. On Classroom it sits 0.46 m off the
rear wall and sees its back side: `backface_fraction` 0.136 from `renderCam` against 0.004 from an
`EYE` placed in the room. That is what step 2 is for — the first look tells you the file is sound,
not that the shot camera is a usable vantage point.

Then fill in `scenes/manifest.json`.

## Reading the contact sheet (`sheet.png`)

```
RGB + eccentricity rings at 10/20/40° | log depth
normals                               | problems: holes red, back-faces magenta
```
* **Red** = rays escaping to the background. Fine through windows onto a proper environment; a defect anywhere else.
* **Magenta** = the eye sees the back of a surface: set dressing built for one shot camera. Decide whether it matters for gaze directions you will use.
* **Nadir/zenith depth** are measured along the EYE's down/up axis: they equal eye height and ceiling clearance only when the EYE is level. That is the metric-scale check.

## Conventions

* Metres; head fixed; `EYE` is a camera object (local −Z = primary gaze, +Y = head up).
* Equirect pixel (u, v) ∈ [0,1]², v = 0 top row, maps to the EYE-frame direction
  `lon = (u−0.5)·2π, lat = (0.5−v)·π, d = (sin lon cos lat, sin lat, −cos lon cos lat)`.
* HDRI scenes put `EYE` at the origin facing world +X, so the equirect render reproduces the source file.

## Verified in Blender 5.2.1 (bpy module, CPU)

* Multilayer EXR writes **one part per pass** by default; readers that only look at part 0 silently see just `Combined`.
  The tools set `use_exr_interleave = True` (single part), and `inspect_preview.py` reads all parts anyway.
* Depth pass for the equirect camera is **ray distance** from the eye centre (matches |P − c| to 3e-7 m); background = 1e10.
* The Normal pass flips back-facing normals toward the camera, so it cannot detect back-faces;
  `preview360.py` renders a separate Backfacing-emission pass for that.
* HDRI mapping: render reproduces the source with zero column shift; a 90° mis-rotated eye is reported as a W/4 shift (negative control).
* Back-face detector: flipping one wall's normals reports 11% of the sphere (positive control).
* No-EYE fallback to the scene camera works, including a scaled camera object.

## Verified on GPU (Blender 5.2.1, OptiX, RTX 4090, 2026-09-12)

The three items below were the open ones in the handover; all three now run.

* **OptiX path.** `setup_device` selects it and all three tiers render on it (1.3–5.2 s at
  2048×1024). The calib-room contact sheet matches the CPU reference in `docs/reference/` structurally,
  and re-running the preview reproduces `report.json` field for field, so the GPU changes nothing
  the checks measure.
* **`fetch_hdris.py` against the live API.** `list` returns 278 indoor HDRIs at ≥16k; `get`
  downloaded `workshop` 8k (339.5 MB) and the md5 matched. The `search` subcommand is still
  unexercised.
* **A real demo file.** Classroom (CC0, Christophe Seux) opens and renders in 5.2. Its
  `_mainScene` is Cycles, metric, unit scale 1.0; the file also carries `dustParticules` and
  `volumeLight`, both EEVEE and neither used here.
* Negative control re-confirmed on GPU: a 90° mis-rotated eye is reported as 512 px = W/4.
* `rel_err_median` has a floor set by the reconstruction filter, not by the mapping or by sample
  count — 16 → 512 spp moves it 0.0152 → 0.0154, while switching to a box filter gives 0.0032.
* Changing `rotation_euler` does **not** update `matrix_world` until the depsgraph runs. Anything
  that repositions the eye must call `bpy.context.view_layer.update()` before `preview360.py`
  reads the pose, or it silently renders the old one.
